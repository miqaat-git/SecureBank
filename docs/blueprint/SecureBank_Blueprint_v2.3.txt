1. Goals and non-goals
Goals
• A complete, working retail-banking simulation: registration, login, accounts, transfers, history, statements, and an admin console.
• Every screen shows real data from MySQL. No hardcoded balances, no fake transactions, no dead buttons.
• A security- and integrity-first design that can be defended in an interview or code review.
Non-goals
• Real money, real KYC, real payment rails, real email/SMS delivery.
• A separate JavaScript frontend application.
• Microservices.
2. Architecture
2.1 Style
A server-rendered Spring MVC monolith. Controllers handle page requests, call services, put view models on the Model, and return a JSP view name. JSPs only render. Business rules live in service classes and nowhere else.
Browser
  -> Spring Security filter chain (session, CSRF, authN/authZ, headers)
  -> Spring MVC controller (binding, validation, flash messages)
  -> Service layer (business rules, @Transactional, ownership checks)
  -> Spring Data JPA repositories (Hibernate)
  -> MySQL 8 (constraints, Flyway-managed schema)
  <- Controller adds view model -> JSP + JSTL + EL -> HTML
REST endpoints exist only where they clearly help interactivity (section 6.4). They reuse the same services and the same security rules.

2.3 JSP-compatible WAR packaging (verified in Phase 0, not assumed)
JSP does not render reliably from an executable JAR, so the project is packaged as a WAR from the first commit.
Planned configuration, each item to be confirmed by the Phase 0 spike:
• <packaging>war</packaging> in the POM.
• Main class extends SpringBootServletInitializer, so the same WAR deploys to standalone Tomcat 10.1.
• spring-boot-starter-tomcat scoped provided for the standalone WAR, with a documented way to run embedded Tomcat locally (spring-boot:run or the executable WAR) that includes tomcat-embed-jasper.

3. Data model (Flyway-managed)
All money columns are BIGINT minor units (paise); the currency is always INR, so no currency column exists. All tables use created_at; mutable tables also use updated_at and a version column.
Money rules (D3). Amounts are stored and calculated as whole paise in a 64-bit integer, and floating-point types are never used for money. User input is parsed from text as a decimal with at most two fractional digits (a third digit is rejected, never rounded), converted exactly to paise and bounded by a maximum so arithmetic cannot overflow. Display uses the ₹ symbol, two decimals and Indian digit grouping (for example ₹1,23,456.78), produced by one shared helper. CSV exports use a plain decimal with no symbol or grouping. Balance, transfer and funding calculations are integer addition and subtraction only, so no rounding occurs.

Integrity rules
• The runtime application account has no UPDATE or DELETE privilege on ledger_entry, audit_log, account_status_history or funding_event, and no DDL privilege at all (3.1); triggers add defense in depth. Corrections are new compensating entries, never edits.
• Invariant checked by tests and by an admin reconciliation view: for every account, balance equals the sum of its ledger entries; total funds change only through funding_event.
• No seed data in migrations except reference data. Demo data is created through the same services as real usage (a clearly labeled dev-only command), so it is never fabricated rows.
Balance write rule (D7). An account balance changes only through the ledger-posting service, as a delta applied inside a row lock together with its ledger entry. No endpoint, form or admin screen can set a balance directly, and the account entity exposes no public balance setter. The ledger is the authoritative record of posted financial changes; the stored balance is a constraint-guarded figure that is reconciled against it.
Account lifecycle (D6). Accounts are created PENDING at zero balance. Only ACTIVE accounts can send transfers, receive transfers or receive funding. FROZEN accounts can do none of these, and this is enforced in the service layer for transfers and funding, not only in the UI (R1). CLOSED and REJECTED are terminal. After a rejection the customer may submit a new application; each rejection and its reason stay in the status history, and at most one PENDING application per account type exists at a time (R2).

3.3 Account number sequence (C4)
• Account numbers come from the number_sequence table. The creating transaction reads the account_number row with a pessimistic write lock (SELECT ... FOR UPDATE), uses the next value, advances it by one and inserts the account, all in one transaction, so two concurrent applications can never receive the same number.
• The number is a configured numeric prefix plus the zero-padded sequence value; the exact length and any check digit are fixed in Phase 1 as configuration.
• A UNIQUE index on account.account_number is the final guard.
• Forbidden: count-then-increment, maximum-plus-one, an in-memory or per-instance counter, a random number without a uniqueness guard, and reusing the auto-increment primary key as the number.
• The number is allocated when the application is submitted (status PENDING), so a rejected application consumes its number; gaps are acceptable and numbers are never reused.
• Only the account package allocates numbers. A concurrency test (Phase 3) creates many accounts at once and asserts distinct numbers.

3.5 Funding corrections are out of scope for v1 (O3)
Limitation. v1 has no reversal, clawback or correction of a funding event, and no screen, API, service method or script in the application edits or deletes a funding_event or ledger_entry row. A mistaken funding stays posted: the funded amount remains in the account and v1 cannot take it back. The reconciliation view still passes, because the posted event and its ledger entry are consistent; the mistake is a business error, not an integrity error. Corrections are not introduced as a feature without a new approval.
Prevention (already in the design). The admin confirm step, the mandatory reason, the per-event maximum, the unique funding reference and the audit trail reduce the chance of a mistaken funding and make it traceable.
Controlled escalation and recovery procedure (documented in the Phase 8 runbook; a manual operating procedure, not an application feature).
• Record. The admin who notices the mistake writes down the funding reference, account number, amount and what was wrong, and reports it to the system owner.
• Contain. An admin may freeze the target account with a reason, using the existing freeze action (R1), so the account neither sends nor receives while the owner decides.
• Decide. The system owner chooses between restoring the database from a backup taken before the funding, rebuilding the demonstration database (the data is fictional), or accepting and documenting the funding as an incident note.
• Recover. Recovery is a restore or rebuild performed by the system owner outside the application. Rows in ledger_entry or funding_event are never edited or deleted, not even by the database owner, and a restore replaces the whole database rather than altering history.
• Close. The account is unfrozen through the normal admin action with a reason, and the incident note is kept with the audit records.
4. Financial operation design
Transaction boundary. One @Transactional service method per money movement. Controllers never open transactions.
Concurrency protection.
• Lock both account rows with pessimistic write locks, always in ascending account-ID order to prevent deadlocks.
• @Version stays on account as a second line of defense; a conflict surfaces as a handled, retry-safe error.
• Phase 4 includes a concurrent-transfer test (many simultaneous transfers on overlapping accounts) that asserts no negative balance, no lost update, and conserved total.
Idempotency. The transfer form carries a server-issued idempotency key. A repeat submission (double click, refresh, back button) with the same key returns the original outcome and never moves money twice. The database unique constraint is the final guard. The same key arriving with a different payload (source, destination or amount) is rejected with a conflict response (HTTP 409 and a form error) and audited; it never returns another request's outcome. The stored transfer, including a FAILED one, is the record the new request is compared against.
Transfer state machine. PENDING (inside the money transaction only) -> COMPLETED, or FAILED with the reason recorded by the separate failure-record transaction described under Auditability. A repeat of a failed submission returns the failed outcome; a retry uses a new form, which carries a new idempotency key. Insufficient funds, frozen or closed accounts, and self-transfer are rejected in the service, and again by database constraints where expressible.
Rules enforced in the service. Ownership of the source account; source and destination accounts are both ACTIVE (a pending, frozen, closed, rejected or unknown destination all return the same generic recipient-unavailable message); amount positive and within configured limits; per-transaction and daily limits (simulated); consistent rounding (none needed with integer minor units).
Auditability. Every completed transfer writes its ledger entries and an audit event in the same transaction. A failed attempt rolls back every balance change; its FAILED transfer record and its audit event are then written in a separate transaction (REQUIRES_NEW), so a failure record can never carry or hide a balance change.
Funding events (D7). Customers cannot deposit or withdraw. Money enters the system only through an administrator funding event, one @Transactional service method that requires the ADMIN role (URL rule plus method security) and a valid CSRF token. It checks the idempotency key and the unique funding reference, locks the target account row and requires status ACTIVE. It then inserts the funding event and its ledger entry with balance_after_minor, applies the amount as a delta inside the lock, and writes the audit record in the same transaction. The amount must be positive and within a configured per-event maximum, and a reason is mandatory. A replay with the same key returns the original event. Any failure rolls back everything, creates no funding_event row, and is audited in a separate transaction. States and transitions are defined in 3.4.
No silent overwrites. Only the ledger-posting service in the ledger package changes a balance. An architecture test fails the build on any other write path, and the reconciliation check (balance equals the sum of ledger entries) runs in tests and in the admin console.
5. Security design
Area
Design
Authentication
Spring Security form login. Passwords hashed with a delegating encoder using bcrypt. Password policy enforced server-side. Generic login errors to avoid user enumeration. User status (3.2) is enforced at sign-in and on every authenticated request.
Brute force
Failed-attempt counter and temporary lockout per account (the LOCKED status with a lock-until time, 3.2), plus basic request throttling on login and registration, and on incorrect current-password attempts at /password, where the endpoint-specific limit never locks the account (5.2).
Sessions
New session ID on login (fixation protection); HttpOnly and SameSite=Lax on every profile, Secure profile-aware (5.1); idle timeout; logout invalidates the session; a user who becomes LOCKED or DISABLED loses all sessions (3.2); optional limit on concurrent sessions.
CSRF
Enabled for every state-changing request. Every form includes the token. Any fetch call sends it in a header.
Authorization
URL rules for coarse access (/admin/** requires ADMIN); method security on services for fine-grained rules.
Object-level ownership
Every customer-facing query is scoped by the authenticated user (for example findByIdAndOwnerId). A resource that is not yours returns 404, not 403, so existence is not revealed. A dedicated test matrix attempts cross-user access on every endpoint.
Output escaping
All dynamic output through c:out or fn:escapeXml. No raw ${} inside script blocks or inline event handlers; data for scripts goes through escaped data- attributes.
Input validation
Bean Validation on form DTOs, enforced server-side. Client-side checks are usability only. Mass assignment prevented by DTOs.
Headers
Content-Security-Policy that disallows inline script, X-Content-Type-Options, frame protection, referrer policy, HSTS in deployment. All JavaScript lives in external files to make this possible.
Error handling
A central controller advice maps exceptions to friendly pages. No stack traces or SQL in responses. Each error shows a correlation ID that matches the server log.
Redirects and exports
Redirect targets validated against an allow-list. CSV exports neutralize leading formula characters.
Secrets and config
Database credentials and secrets come from environment or external config, never from the repository. The running application receives only the least-privilege application account; migration credentials go only to the migration step (3.1).
Audit
Login success and failure, lockouts, password changes, transfers, admin actions (including user status changes) and account lifecycle changes are logged to audit_log. Roles are fixed at creation (D2); v1 has no role-change feature and records no role-change events.
Administrative actions
Approvals, freezes and funding require the ADMIN role through both URL rules and method security. Each needs a CSRF token and a mandatory reason, funding also needs an idempotency key, and every outcome including denials is audited. Admins cannot own customer accounts, so they cannot fund themselves (D2).
Initial administrator (D9)
A startup runner creates the first admin only when none exists, from environment-supplied credentials, and forces a password change at first login. No default credentials exist in the repository. A one-time database row with a unique key makes concurrent duplicate bootstrap impossible. Passwords are never hardcoded or logged. A documented recovery procedure for a lost admin runs only when no enabled admin exists, uses the same environment path, and is audited.
MFA readiness (D4)
MFA is not implemented in v1 and is never described as implemented. Authentication runs through one configurable provider and success-handler chain, so a second factor can be added later without reworking sessions or the user table.
History API (C2)
One read-only endpoint, GET /api/accounts/{id}/transactions, behind the same session and filter chain as the pages: authentication required, CUSTOMER role, owner-scoped lookup with 404 for any other account, server-side size and page limits, validated parameters, JSON errors with a correlation ID. Full contract in 6.4.
Secure cookie (C8)
Profile-aware: required in production, relaxed only in the explicitly selected dev profile (5.1).
Forced password change (O1, D9)
A server-side filter limits a user whose must_change_password flag is set to the password-change workflow, logout and their supporting endpoints; the rule is enforced on every request and not only in the navigation (5.2).

5.2 Forced password change gate (O1)
• One password-change function, /password, serves both roles. Profile editing (/profile) stays customer-only, and an admin has no profile page.
• The gate is a server-side filter in the Spring Security chain, after authentication. On every authenticated request it reads must_change_password together with the user status (3.2) from the database, so a session opened before the flag was set is gated at its next request.
• While the flag is set, only the requests in the table below are allowed. Browser page requests to anything else receive a redirect to /password; any other method, and every /api/** call, receives 403 with the code PASSWORD_CHANGE_REQUIRED and no redirect. Refusals are logged with the correlation ID.
Request while the flag is set
Allowed
Why
GET and POST /password
Yes
The only way to clear the flag; the form carries a CSRF token and re-renders with field errors on a wrong current password, a policy violation or a repeated old password, without redirecting, so there is no loop.
POST /logout (with CSRF token)
Yes
The user can always sign out, so the gate can never trap a session.
Static assets used by the password page and the layout (stylesheet, script and icon files)
Yes
Lets the password page render and lets its script load.
/error and the 401, 403 and 404 pages
Yes
Error handling must work.
Everything else, including /, /dashboard, /accounts/**, /transfers/**, /transactions, /profile, /admin/** and /api/**
No
Redirect to /password for page requests; 403 PASSWORD_CHANGE_REQUIRED for API and non-GET requests.
• After a successful sign-in, the success handler sends a flagged user to /password. The layout tag file shows a flagged user only Change password and Sign out; this is a convenience, and the filter is the control.
• The password change requires the current password, a new password that meets the password policy and differs from the current one (I8; enforced in PasswordService in the service layer, not only in the form, for the voluntary and the forced change and for both roles), and a matching confirmation. In one transaction it stores the new hash, clears must_change_password and writes the audit record; the same session then continues to the user's home page with a flash message.
• The flag is set only by the first-administrator bootstrap and the lost-admin recovery path (D9). v1 has no admin-initiated password reset, so the flag is never set for a customer in normal operation, but the gate applies to any user who has it, and tests cover both roles.
• Throttling of POST /password (N1). It is enforced on the server in the service layer and never relies on JavaScript.
  - Every incorrect current-password attempt counts toward the shared request throttle (section 5, brute-force row) and toward an endpoint-specific limit held per authenticated user. Default: 5 incorrect attempts within 15 minutes, configurable through securebank.security.password-change.max-failures and securebank.security.password-change.window.
  - When the limit is reached, further POST /password requests are refused with HTTP 429 and the friendly message "Too many attempts. Please wait a while and try again." until 15 minutes after the attempt that reached the limit. While the user is throttled the submitted current password is not checked at all, so a correct password does not bypass the throttle, and the response reveals nothing about password verification. Refused requests are not counted again, so they cannot extend the wait. GET /password still works.
  - The throttle never changes the user's status to LOCKED, never ends a session, and does not affect sign-in, logout, the forced-change gate or any other page. Login-lockout behavior (3.2) is unchanged.
  - An incorrect current password produces the generic form message "The password could not be changed. Check your details and try again.", with no detail about why verification failed. A policy violation or a reused password (I8) shows a field message about the new password and is not counted, because the current password was correct.
  - A successful password change resets the user's counter.
  - The counter is kept in memory by the application, per user and per instance, using no external rate-limiting dependency and no new table. It resets when the application restarts; this is accepted for the single-instance simulator, and the audit log is the durable record (section 11).
  - Passwords, password hashes and submitted password fields are never logged or stored in audit rows: the form object excludes them from toString and a log-scrubbing test covers /password.
  - Audit events, without secrets and with user id, IP, correlation ID and a reason code: PASSWORD_CHANGE_SUCCEEDED; PASSWORD_CHANGE_FAILED with reason CURRENT_PASSWORD_INCORRECT, REUSE or POLICY; PASSWORD_CHANGE_THROTTLED, written once when the limit is reached. Later refused requests in the same period are logged with the correlation ID but not audited, to avoid flooding the audit log.
6. Frontend design
6.1 Principles
Polished, responsive, accessible, consistent. Mobile-first CSS with design tokens (color, spacing, type scale) in one stylesheet system. Simulator labeling. Every page carries a persistent footer reading: Educational banking simulator. Fictional customers and simulated funds. Not a real bank. The landing and registration pages say the same in their main content, and the README and every phase report repeat it.

• One layout tag file wraps every page (header, navigation, flash messages, footer).

Aspect
Contract
Method and route
GET /api/accounts/{id}/transactions. Read-only; no state changes.
Authentication
The same session cookie and security chain as the pages. An anonymous caller receives a 401 JSON response (no redirect to the login page); a LOCKED or DISABLED user receives 401.
Authorization
CUSTOMER role through the URL rule and method security; an ADMIN receives 403. The service loads the account with findByIdAndOwnerId; an account that is not the caller's and one that does not exist return the identical 404 body. Accounts of any status, including CLOSED, can be read.
Pagination limits
page: whole number, 0 or more, default 0. size: whole number from 1 to 50, default 20 (the history page size). Values outside the range are rejected with 400, never silently changed. Rows are ordered by posted time then id, descending, so pages are stable. The response says whether a next page exists, without a count query.
Filters and validation
The same filters and the same validator as the history page: from and to dates (from must not be after to), direction (CREDIT or DEBIT), and status. Unknown or malformed values return 400 with field-level detail. The account id must be a whole number.
Response
JSON with items, page, size and hasNext. Each item carries the same fields as the JSP row model and nothing more; amounts are given as integer paise plus a display string formatted by the shared money helper (D3).
Errors
A JSON body with status, code, message and correlationId, produced by an advice limited to the web.api package: VALIDATION_ERROR 400, UNAUTHENTICATED 401, FORBIDDEN 403, NOT_FOUND 404, METHOD_NOT_ALLOWED 405, TOO_MANY_REQUESTS 429 (shared request throttle), INTERNAL_ERROR 500. No stack trace, SQL or internal text; the correlation ID matches the server log and the X-Correlation-Id header.
Response headers
Content-Type application/json; Cache-Control no-store; X-Content-Type-Options nosniff. CSRF tokens are not needed because the call changes nothing.
Client rules
The script builds rows with textContent, never innerHTML; it reads no data from inline attributes beyond escaped data- attributes; it shows a loading state (aria-busy) and an error message with the correlation ID.

8. Test strategy
8.1 Layers
• Unit tests for services and the Money type (business rules, limits, state machine), with JUnit 5 and Mockito.
• Repository and migration tests against a real MySQL 8 (Testcontainers; this needs Docker available on your machine, which is a prerequisite to confirm in Phase 0).
• Web-layer tests with MockMvc and Spring Security Test (CSRF, roles, validation errors, redirects).
• Rendered-page tests over real HTTP against embedded Tomcat, because MockMvc does not execute the JSP engine and cannot prove that a JSP actually renders.
• Concurrency and idempotency tests for transfers (section 4).
• Authorization matrix tests: every endpoint as anonymous, owner, other customer, and admin.
• Accessibility checks: an automated scan on key pages plus a manual keyboard and screen-reader checklist per phase.
• Funding and lifecycle tests. Admin-only access, unique reference and idempotent replay, atomic rollback on failure, funding refused for non-ACTIVE accounts, concurrent funding and transfers conserving totals, every account-status transition (allowed and forbidden), an architecture test that no other code path writes a balance, and a check that no customer deposit or withdraw route exists (the authorization matrix expects 404 or 405).
• Money and role tests. Parsing rejects a third decimal, negatives, zero where not allowed, non-numeric text and over-limit amounts; display uses Indian grouping; CSV output is plain; a static check bans floating-point types in money code; an admin cannot open or own an account, and a user cannot hold both roles.
• Bootstrap and application tests. Concurrent startups create exactly one admin; no password appears in logs; a second PENDING application of the same type is refused; re-application after a rejection is accepted and the history keeps both.
• User status and session tests (C5). Every user-status transition, allowed and forbidden; sign-in results and messages for each status; a temporary lock clears at the first attempt after its time; locking or disabling a user ends an open session at once (two browsers) and a missed invalidation still ends it on the next request; the self-lock and last-admin guards; the must_change_password gate.
• Account number tests (C4). Many concurrent account creations produce distinct numbers; the UNIQUE index rejects a forced duplicate; a static check finds no count-then-increment or maximum-plus-one code.
• Funding lifecycle tests (C6). A posted event has exactly one ledger entry and the exact balance delta; a failure at each step leaves no funding_event row and no balance change and writes the failure audit in its own transaction; a replay returns the original event; the same key with a different payload is refused; no setter or update path exists.
• Database privilege tests (C7). Under the application account, UPDATE and DELETE on ledger_entry, audit_log, account_status_history and funding_event are refused, DDL is refused, and the production configuration contains no migration credentials.
• Profile and cookie tests (C8). The prod profile sets Secure on the session cookie and sends HSTS; startup fails if prod has Secure off; the dev profile behaves as documented; HttpOnly and SameSite are present in every profile.
• History API tests (C2). Anonymous 401 JSON, ADMIN 403, another customer's account 404 identical to a missing account, owner 200; page and size at and beyond their limits, non-numeric values, bad date ranges and unknown directions return 400; stable ordering across pages; fields equal the JSP row model; error body carries the correlation ID; Cache-Control no-store.
• Navigation tests (C1). For each role, every navigation link resolves to a route in section 7 and returns the expected status; the Accounts and History index routes pass the ownership matrix.
• Tooling checks (C9). Service unit tests use Mockito; the command-line Maven build reproduces the WAR; the NetBeans build and deploy is a manual-only check and is labeled that way in the phase report.
• Forced password change tests (O1, I8). For both a CUSTOMER and an ADMIN with the flag set: every route in section 7 other than /password and POST /logout is refused (redirect for page requests, 403 PASSWORD_CHANGE_REQUIRED for API and non-GET requests); a direct POST is refused without any navigation; /password renders with its assets; logout with a CSRF token works and does not loop; a wrong current password, a policy violation or reuse of the old password re-renders the form with no redirect loop; success clears the flag and the same session reaches its home page; a session opened before the flag was set is gated at its next request; the new password must differ from the current one; the change is audited.
• Role and audit tests (O2). No endpoint or service changes a user's role, and no role-change audit event exists.
• Funding correction absence tests (O3). An architecture test finds no service method, controller or script that updates or deletes funding_event or ledger_entry rows, and the authorization matrix finds no reversal or correction route (expected 404 or 405).
• Idempotency conflict tests (I6). The same key with a different payload returns 409 for transfers and for funding, is audited, and never returns another request's outcome.
• Password-change throttle tests (N1). Repeated incorrect current passwords return the generic form message and are counted by both the shared throttle and the endpoint limit; at the configured limit (default 5 in 15 minutes) the next POST /password returns 429 with the friendly message and does not check the password, even a correct one; the user's status stays ACTIVE and the user can still sign in, sign out and use other pages (no account lock); the throttle is per user, so another user is unaffected; the endpoint recovers when the window passes (tested with an injected clock); a successful change resets the counter; throttled and generic responses contain no password-verification detail; passwords, hashes and submitted password fields never appear in logs or audit rows (log-scrubbing test extended to /password); the audit events listed in 5.2 are written without secrets; login-lockout behavior is unchanged (regression test); the behavior is identical with JavaScript disabled.
• Password reuse tests (I8). The service layer rejects a new password equal to the current one when called directly, bypassing the form, for a CUSTOMER and for an ADMIN, in the voluntary change and in the forced workflow; the rejection is audited without secrets, is not counted by the throttle and leaves must_change_password set; a different valid password succeeds and clears the flag.
• Route phase tests (N2). The landing page / is public and renders in Phase 2; /profile returns 200 for a CUSTOMER, 403 for an ADMIN and a redirect to the login page for an anonymous user; the Profile navigation entry is absent before Phase 3, present afterwards for CUSTOMERs, and never shown to an ADMIN.

12. Reference Project Analysis and Adaptation Plan
The uploaded project is a backend-only Spring Boot 2.7 microservices banking API with no user interface, so it informs SecureBank's domain rules and its list of mistakes to avoid, not its look, its architecture or its code.
Every finding below comes from files extracted and read from the uploaded archive. Nothing was run, built or modified.
• No frontend exists. The project source contains no JSP, HTML, CSS, JavaScript, image or template files. The only HTML in the archive is generated Javadoc under docs/, together with its bundled scripts, stylesheets and images. There is no dashboard, navigation, form or visual design to preserve.
• Stack is older than the approved one. All seven modules use Spring Boot 2.7.14 or 2.7.15 with Spring Cloud 2021.0.8, Java 17 and javax.persistence imports. The approved Boot 3 / Jakarta stack is a migration away, and Boot 2.7 is itself long out of support.
• Architecture is distributed. An API gateway, a Eureka registry, Keycloak, Feign clients and five MySQL databases, one per service. A single transfer touches three services over HTTP.
• Money handling is unsafe. There is no @Transactional on any account, transfer or transaction service (the only @Transactional in the archive is on the non-financial UserServiceImpl), no locking, no @Version, no idempotency, and the three remote calls of a transfer can fail halfway and leave inconsistent balances.
• Several business rules are broken or untested. Closing an account never saves the change, the status-update rule is inverted, and the only tests found are empty context-load tests.
• Committed secrets. Keycloak client secrets and database root credentials sit in plain application.yml files. Their values are deliberately not reproduced in this document.
• Useful domain ideas do exist. Account and user approval states, a reference ID tying a transfer to its ledger rows, account lifecycle states, and a clean service/controller/DTO split are worth carrying over in concept.
